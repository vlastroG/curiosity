# Thought Forge

Неделя 1, день 3 — разные способы рассуждения.

Одна и та же задача решается через API четырьмя способами. Способ задаётся только
system prompt'ом и числом вызовов модели: сам вопрос пользователя не меняется.
Есть две вкладки — чат с переключалкой режимов и экран сравнения, который прогоняет
один вопрос через все четыре режима сразу.

## Режимы

| Режим | Что уходит в system prompt | Вызовов |
| --- | --- | --- |
| **Прямой ответ** | ничего, system-сообщение не отправляется вовсе | 1 |
| **Пошагово** | требование разбить решение на пронумерованные шаги, выписывать промежуточные результаты, проверить решение и закончить строкой `Ответ:` | 1 |
| **Предпромпт** | вызов 1 — «ты инженер промптов, не решай задачу, составь промпт для её решения»; вызов 2 — сгенерированный текст идёт как system prompt | 2 |
| **Совет экспертов** | три ролевых промпта параллельно (аналитик, инженер, критик), затем модератор сводит мнения | 4 |

Критик в параллельной схеме не критикует чужие решения — при одновременном запуске
их ещё нет. Вместо этого он сначала перечисляет ловушки задачи, а потом решает сам,
обходя их. Расхождения между экспертами разбирает модератор на четвёртом вызове.

Промежуточные артефакты видны в интерфейсе: у «Предпромпта» раскрывается
сгенерированный промпт, у «Совета экспертов» — три отдельных мнения.

Параметры сэмплинга одинаковы для всех режимов и намеренно не выведены в интерфейс
(`temperature = 0.2`, `max_tokens = 4000`, см. `src/api.js`): разница в ответах должна
идти от способа рассуждения, а не от настроек генерации.

## Сравнение

Модель — `deepseek-v4-flash` (см. `src/api.js`). Это рассуждающая модель: в ответе API
приходит отдельное поле `reasoning_content`, и эти токены учитываются в `completion_tokens`.
Важное следствие для темы дня — модель рассуждает пошагово сама, даже когда её об этом
не просят.

Задача с проверяемым ответом и классической ловушкой — легко забыть длину самого поезда:

> Поезд длиной 200 метров движется с постоянной скоростью 72 км/ч и въезжает в тоннель
> длиной 1300 метров. Сколько секунд пройдёт с момента, когда локомотив въехал в тоннель,
> до момента, когда последний вагон полностью покинул тоннель?

Верный ответ — **75 с**: путь равен 1300 + 200 = 1500 м, скорость 20 м/с.
Типичная ошибка — 65 с (забыта длина поезда).

Два прогона одного и того же вопроса:

| Режим | Прогон 1 | Прогон 2 | Токены (1 / 2) | Время (1 / 2) |
| --- | --- | --- | --- | --- |
| Прямой ответ | **75** ✓ | **75** ✓ | 386 / 345 | 3.4 с / 2.6 с |
| Пошагово | **75** ✓ | **75** ✓ | 797 / 781 | 4.8 с / 4.7 с |
| Предпромпт | **75** ✓ | **75** ✓ | 2217 / 2702 | 10.2 с / 13.1 с |
| Совет экспертов | **75** ✓ | **75** ✓ | 3402 / 3111 | 12.4 с / 11.7 с |

### Отличаются ли ответы

По итоговому числу — нет: все четыре режима дали 75 в обоих прогонах. Отличается то,
что видит пользователь. «Прямой ответ» печатает голое `75`: весь разбор остался
в `reasoning_content` и до экрана не дошёл. «Пошагово» переносит то же рассуждение
в видимый ответ — с блоком «Дано», промежуточными результатами и проверкой подстановкой.
«Совет экспертов» добавляет сверху явное сопоставление трёх решений.

### Какой способ дал наиболее точный результат

По точности все четыре одинаковы, поэтому разделять их приходится по цене:
режимы отличаются примерно в 9 раз по токенам (386 против 3402) и в 4 раза по времени
(3.4 с против 12.4 с) при одном и том же ответе.

Причина в том, что модель рассуждающая. Инструкция «решай пошагово» не добавляет ей
рассуждения — оно и так есть, — а лишь делает его видимым. Поэтому на `deepseek-v4-flash`
эти способы стоит выбирать не ради точности, а ради того, что нужно на выходе:

- **Прямой ответ** — когда нужен только результат. Самый дешёвый и быстрый.
- **Пошагово** — когда нужно показать ход решения человеку или проверить его.
- **Предпромпт** — окупается на расплывчатых задачах, где неочевиден сам метод решения;
  на задаче с одной формулой это просто удвоение стоимости.
- **Совет экспертов** — окупается там, где эксперты реально расходятся и модератору
  есть что разбирать. Здесь все трое пришли к 75 одинаковым путём, и четыре вызова
  ушли на подтверждение того, что один вызов выдал за 3 секунды.

### Ловушка: max_tokens включает рассуждение

Самая дорогая ошибка при работе с рассуждающей моделью — считать, что `max_tokens`
ограничивает длину ответа. На самом деле это общий бюджет на `reasoning_content`
и на `content` вместе, причём рассуждение расходуется первым. Если оно выбирает лимит
целиком, приходит `finish_reason: "length"` и **пустой** `content`:

| Модель | max_tokens | finish_reason | Длина ответа | Токенов на рассуждение |
| --- | --- | --- | --- | --- |
| `deepseek-v4-pro` | 300 | `length` | 0 | 300 |
| `deepseek-v4-flash` | 300 | `length` | 0 | 300 |
| `deepseek-v4-flash` | 1500 | `stop` | 332 символа | 440 |

Поэтому `MAX_TOKENS` поднят до 4000, а интерфейс больше не показывает пустую панель молча:
в мета-строке появляется красный бейдж `finish: length`, а вместо ответа выводится
объяснение, куда делся текст (`Answer` в `src/App.jsx`). Это важно как раз для «Совета
экспертов»: там обрезаться может один эксперт из трёх, и без пометки это выглядит
как случайный сбой.

### Отдельно про «Предпромпт» на нерассуждающей модели

До перехода на семейство v4 та же задача прогонялась на `deepseek-chat`, и там «Предпромпт»
в одном из двух прогонов ошибся — выдал **150** вместо 75.

Сгенерированный промпт был хорошим: он сам вывел верный путь решения (1300 + 200 = 1500 м),
перечислил типичные ошибки и описал самопроверку. Но последней строкой добавил:
«Формат ответа: только число, без единиц измерения и пояснений». На втором вызове модель
выполнила это буквально — посчитала без единого промежуточного шага и ошиблась.

Вывод, который переносится и на другие модели: оптимизируя промпт, модель склонна ужимать
формат вывода и тем самым отбирает у себя же право рассуждать вслух. Для модели без
внутреннего рассуждения это прямо бьёт по точности; модели семейства v4 такой промпт
переживают только потому, что рассуждают в `reasoning_content`, куда запрет на пояснения
не достаёт.

## Запуск

```bash
docker compose -f src/thought-forge/docker-compose.yml up --build
```

Затем http://localhost:5175

Без compose:

```bash
docker build -t thought-forge ./src/thought-forge
docker run -p 5175:80 -e DEEPSEEK_API_KEY=sk-your-key-here thought-forge
```

Ключ берётся из `.env` в корне репозитория (`DEEPSEEK_API_KEY=...`). При старте контейнера
`docker-entrypoint.sh` записывает его в `env-config.js`, откуда он попадает в `window._env_`.

## Ограничение по безопасности

Бэкенда нет: собранная статика отдаётся nginx, а запросы к DeepSeek уходят прямо из браузера.
Значит, ключ виден в исходниках страницы любому, кто её откроет. Для локального учебного
приложения это приемлемо, для публичного развёртывания — нет: там нужен серверный прокси,
который держит ключ у себя.
