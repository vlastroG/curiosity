# Agent Sprout

Помощник начинающего строителя. Неделя 2, дни 6-11: агент как отдельная сущность
(день 6), работа с токенами (день 8), сжатие истории (день 9), три стратегии
управления контекстом (день 10) и модель памяти с доменной машиной состояний (день 11).

Интерфейс на React, бэкенд-прокси на Go, между ними REST. Вся работа с LLM спрятана
в один Go-пакет — это и есть «коробка» агента: запрос входит, проходит входную политику,
превращается в вызов модели и проверяется выходной политикой. Браузер про DeepSeek
не знает ничего и ходит только на собственный бэкенд.

## Чем это отличается от дней 1–5

В днях 1–5 бэкенда не было: собранная статика отдавалась nginx, ключ через
`docker-entrypoint.sh` попадал в `window._env_`, и запросы уходили в DeepSeek прямо
из браузера. Ключ был виден любому, кто открыл страницу — в README дня 5 это записано
как ограничение.

Здесь ключи читает только Go-процесс. В отдаваемой странице, в бандле и в ответах API
их нет.

## Коробка агента

```
запрос пользователя
      │
      ▼
┌─────────────────┐   пустой запрос, превышен лимит длины,
│  input policy   │   похоже на подмену инструкций
└────────┬────────┘   → отказ ДО вызова модели, ноль потраченных токенов
         ▼
┌─────────────────┐   диспетчер разбирает сообщение, страж разрешает переход:
│ машина состояний│   завести задачу, собирать данные, сверить или выдать план
└────────┬────────┘
         ▼
┌─────────────────┐   окно заполнилось -- сворачиваем его в пересказ отдельным
│ сжатие истории  │   вызовом модели
└────────┬────────┘
         ▼
┌─────────────────┐   доменная роль + знания + итоги задач + пересказ окна
│ сборка контекста│   + рабочая память задачи + сообщения окна + инструкция хода
└────────┬────────┘
         ▼
┌─────────────────┐   один POST на эндпоинт провайдера выбранной модели,
│  вызов модели   │   замер времени, разбор usage
└────────┬────────┘
         ▼
┌─────────────────┐   пустой ответ (весь бюджет ушёл в рассуждение),
│  output policy  │   обрезка по max_tokens
└────────┬────────┘   → жёсткие нарушения блокируют, мягкие дают предупреждение
         ▼
┌─────────────────┐   задача закрыта планом -- её итог сжимается в пересказ
│ закрытие задачи │   и переезжает в краткосрочную память диалога
└────────┬────────┘
         ▼
   ответ + метрики + трейс всех этапов
```

Код коробки — `backend/internal/agent`. Пакет не импортирует ни `net/http`, ни хранилище:
единственная точка входа — `Agent.Run(ctx, RunInput) (RunOutput, error)`. Поэтому весь
конвейер прогоняется в тестах с подставным клиентом модели — без сети, ключей и денег.

| Пакет | Ответственность |
| --- | --- |
| `internal/agent` | конвейер, политики, память, машина состояний, каталог моделей и расчёт стоимости |
| `internal/llm` | OpenAI-совместимый клиент; провайдер приходит аргументом |
| `internal/store` | чаты, ветки, задачи и справочник знаний: всё в памяти + снапшот в JSON-файл |
| `internal/httpapi` | REST-обвязка: разобрать запрос, позвать агента, сложить результат |

## Настройки чата

Каждый чат — отдельный агент со своим характером. Всё редактируется в правой панели
и хранится вместе с чатом.

Редактируемых настроек ровно четыре:

| Настройка | Что делает |
| --- | --- |
| `model` | какая модель отвечает (см. каталог ниже) |
| `temperature` | разброс ответов, 0–2 |
| `historyDepth` | размер окна истории: сколько сообщений уходит в модель как есть |
| `maxInputChars` | потолок длины запроса для входной политики |

`max_tokens` в панели показан, но не редактируется: он выводится из модели
и пересчитывается при её смене — см. «Дефолты берутся из модели» в разделе дня 11.

Остальное убрано в день 11 вместе с разворотом проекта в домен: формат ответа
и лимит слов противоречат детальному плану работ, `top_p` и штрафы на него не влияют,
сжатие истории стало безусловным, а судья дня 10 к домену отношения не имеет.
Доменная роль помощника строителя задана в коде, скрыта и не редактируется —
см. раздел про день 11.

Доллары за 1 млн токенов по пиковому тарифу. Источник — https://api-docs.deepseek.com/quick_start/pricing/,
снято 2026-09-14. Каталог целиком лежит в `backend/internal/agent/catalog.go` и отдаётся
интерфейсу через `GET /api/catalog`, так что цены не продублированы на фронте.

`deepseek-v4-flash` переименован в **`deepseek-flash`** (это DeepSeek-V4.1-Flash), прежняя
модель снята, а старое имя провайдер пока принимает и обслуживает новой. Заодно втрое
подешевел: было $0.44 / $1.32 за промах и выход, стало $0.3 / $1.2. Прежний id у нас
остаётся синонимом (`modelAliases` в каталоге) — чтобы чаты, заведённые до переименования,
не встречали пользователя словами «неизвестная модель».

Две особенности прайса DeepSeek, которые учитывает расчёт:

- **Кеш промпта.** Вход тарифицируется по двум ставкам, разбивку провайдер присылает
  в `usage` (`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`). Считаем по ней:
  на длинной истории разница в десятки раз. Провайдеры без такой разбивки
  (OpenRouter) считаются целиком по ставке промаха — верхняя оценка.
- **Peak / off-peak.** Пик — 01:00–04:00 и 06:00–10:00 UTC по будням, в остальное время
  вдвое дешевле. В метриках сообщения помечено, по какому тарифу посчитано.

Бесплатная модель OpenRouter нужна как рабочая лошадка для отладки: на ней гоняются
проверки, не тратя денег. Если она отвечает «No endpoints found matching your data policy»,
в настройках приватности OpenRouter надо разрешить бесплатных провайдеров.

## День 8 — токены

### Что вообще отдаёт API

В ответе на каждый вызов приходит объект `usage`, и это единственный источник чисел:

```json
"usage": {
  "prompt_tokens": 144,
  "completion_tokens": 329,
  "total_tokens": 473,
  "prompt_cache_hit_tokens": 0,
  "prompt_cache_miss_tokens": 0,
  "completion_tokens_details": { "reasoning_tokens": 324 }
}
```

| Поле | Что это |
| --- | --- |
| `prompt_tokens` | **весь вход вызова одним числом**: system prompt + вся отправленная история + новый вопрос |
| `completion_tokens` | весь выход этого вызова |
| `reasoning_tokens` | часть `completion_tokens`, ушедшая во внутреннее рассуждение. Оплачивается, но в видимый текст не попадает и в историю следующего запроса не уезжает |
| `prompt_cache_hit/miss_tokens` | разбивка входа по кешу промпта, нужна для денег. Присылает только DeepSeek |

Разбивки по отдельным сообщениям в API нет, и эндпоинта для подсчёта токенов тоже нет.
Поэтому вес отдельного сообщения в отрыве от запроса в интерфейсе нигде не показывается:
никаких оценок и эвристик в проекте нет, все цифры взяты из ответов провайдера.

### Почему числа соседних ходов не сходятся

Диалога «на сервере» у модели не существует: каждый запрос уезжает целиком заново.
Значит `prompt_tokens` растёт с каждым ходом, а `completion_tokens` — нет, и сравнивать
их между собой бессмысленно. Реальный прогон:

```
ход 1   вход 142   выход 171 (из них 143 на рассуждение)
ход 2   вход 188   выход  71 (из них  55 на рассуждение)
```

Прирост входа `188 − 142 = 46` — это видимая часть первого ответа (`171 − 143 = 28`)
плюс второй вопрос плюс накладные на обёртку сообщений. До дня 8 обе цифры стояли
одной строкой через стрелку под ответом (`142 → 171`, потом `188 → 71`), и понять,
почему `171` и `188` не бьются, было невозможно.

Теперь метрики хода разнесены по двум сообщениям:

- **под вопросом пользователя** — `вход N tok`, прирост к прошлому запросу, сколько
  сообщений истории уехало, попадания в кеш и деньги за вход;
- **под ответом модели** — `выход N tok (из них R на рассуждение)`, деньги за выход,
  время, `finish_reason` если не `stop`, и «итого за ход» вместе со служебными вызовами.

В шапке чата — `Σ вход` и `Σ выход` по отдельности: видно, что вход растёт быстрее
выхода. Обе суммы считаются ровно по тем числам, что стоят в ленте, поэтому итог
сходится с тем, что видно глазами.

### Окно контекста

Под шапкой — полоска, как в Claude Code:

```
контекст ▓▓▓░░░░░░░  204 + 8 192 резерв из 65 000 (12.9%) · осталось 56 604 под новый вопрос
```

Считается по факту, без оценок:

- **занято** = `prompt_tokens` последнего запроса + видимая часть последнего ответа.
  Ровно это уедет в модель в следующий раз;
- **резерв** = `max_tokens`. Место под будущий ответ занимает окно наравне с входом —
  провайдер требует, чтобы вход и резерв вместе помещались в лимит модели;
- от 80% полоска желтеет и предупреждает, при заполнении краснеет, а поле ввода
  и кнопка отправки гаснут.

Оговорка: если глубина истории меньше длины диалога, старые сообщения выпадают
из запроса и реальный вход может оказаться меньше показанного. Индикатор в этом случае
завышает занятое — завысить безопаснее, чем занизить и упереться в отказ провайдера.

### Что ломается при переполнении

Три разных случая, и они различаются в интерфейсе:

1. **Окно кончилось до отправки.** Отправка блокируется в интерфейсе, а если постучать
   в API мимо него — входная политика отвечает 422 с кодом `input_policy`, не потратив
   ни одного токена.
2. **Не влез сам вопрос.** Индикатор считает только уже отправленное и не знает, какой
   длины будет новый вопрос, поэтому длинную простыню всё равно отобьёт провайдер.
   Такой ответ распознаётся отдельно и приходит с кодом `context_overflow` и плашкой
   «переполнение контекста» вместо сырого сбоя провайдера.
3. **Ответ обрезан по `max_tokens`.** Выходная политика ставит предупреждение
   `finish_reason: length`, а если весь бюджет ушёл в рассуждение и видимого текста
   не осталось — блокирует пустой ответ с объяснением.

Отдельно про ловушку, которую видно только на переполнении: вопрос, чей вызов
не состоялся, **не попадает в контекст**. Иначе не влезшая простыня оставалась бы
в истории, каждая следующая попытка была бы тяжелее предыдущей, и выбраться
из переполнения можно было бы только очисткой чата. В реальном прогоне до этой правки
второй запрос весил 74 382 токена, третий — уже 88 400, хотя вопрос был втрое короче.

### Как воспроизвести три диалога из задания

Короткий и длинный — обычная переписка, цифры видны под каждым сообщением.
Для переполнения на бесплатной модели (окно 65 000 токенов) удобнее всего поднять
в настройках чата лимит длины запроса до 100 000 символов и вставить пару больших
текстов: 90 000 символов русского текста дают около 27 000 токенов, так что третья-четвёртая
простыня упирается в окно. Поднять `max_tokens`, чтобы резерв съел окно, на бесплатной
модели не выйдет: у неё потолок вывода те же 4 096.

## День 9 — сжатие истории

Диалога «на сервере» у модели нет, поэтому память агента приходится строить самому.
До дня 9 это был скользящий хвост: `historyDepth` последних сообщений уезжали как есть,
всё, что старше, исчезало без следа. Теперь это **окно со сжатием**.

### Схема

```
окно 1: msg1 … msgN                        → уходят в модель как есть
                  ↓ приходит msgN+1
            пересказ₁ = сжать(msg1…msgN)
окно 2: msgN+1 … msg2N  + пересказ₁          → в модель: пересказ₁ + окно 2
                  ↓ приходит msg2N+1
            пересказ₂ = сжать(пересказ₁ + окно 2)
окно 3: msg2N+1 …       + пересказ₂          → в модель: пересказ₂ + окно 3
```

В запрос всегда уезжает: system prompt чата → текущий пересказ (если есть) →
сообщения текущего окна → новый вопрос. Пересказ подставляется вторым
`system`-сообщением: это память агента, а не реплика собеседника.

Память копится рекурсивно — каждое следующее сжатие складывает прошлый пересказ
с новым окном, — поэтому вход не растёт линейно вместе с диалогом.

### Тумблера больше нет

В день 9 сжатие включалось галочкой, и выключенная она означала «окно просто теряется».
В дне 11 галочка убрана: закрывшееся окно сворачивается в пересказ всегда. Настройка,
у которой один вариант — «агент забудет начало разговора», не выбор, а способ однажды
удивиться; один служебный вызов на каждые N сообщений дешевле потерянного контекста.

`historyDepth = 0` — особый случай и заодно замена тумблеру: памяти нет вовсе,
ни сообщений, ни пересказа, и сжимать нечего.

Сжатие делает та же модель, что отвечает в чате. Если её вызов упал, **ход отменяется
целиком**: без пересказа окно уже нельзя выбросить, а отправлять его как есть значит
делать вид, что сжатия не было. Пользователь повторяет запрос, и пересказ собирается
заново — упавший вопрос при этом в контекст не тащится, потому что в окно попадают
только состоявшиеся обмены.

### Что видно в ленте

На каждом закрытии окна появляется плашка во всю ширину. Со сжатием — спокойная:

```
──────── история сжата ────────
свёрнуто 4 сообщения · пересказ 264 tok, ещё 177 на рассуждение · $0 · 2.7 с
▸ показать пересказ
```

Разворачивается в текст пересказа — ровно то, что теперь уезжает в модель вместо
свёрнутых сообщений.

Сами свёрнутые сообщения из ленты никуда не деваются: сжимается то, что отправляется
в модель, а не то, что видит человек.

Токены и деньги служебного вызова живут на самой плашке, а не в метриках хода:
так каждая цифра в ленте принадлежит ровно одному сообщению, и суммы в шапке сходятся
с тем, что видно глазами.

### Прогон на бесплатной модели

Окно 4, сжатие включено, `liquid/lfm-2.5-2.6b:free`:

```
ход 1   вход 237   история 0
ход 2   вход 303   история 2
ход 3   вход 359   история 0   ← окно закрылось: 4 сообщения → пересказ 264 tok
ход 4   вход 383   история 2
ход 5   вход 387   история 0   ← второе сжатие, уже рекурсивное
```

Тот же диалог без сжатия давал бы на третьем ходе вход 230 вместо 359: окно просто
выброшено. Разница в 130 токенов — это и есть цена памяти; с дня 11 мы платим её
всегда, потому что альтернатива — агент, забывший, о чём шла речь.

Оговорка про качество: модель на 2.6B параметров пересказ делает сносно, но на втором,
рекурсивном сжатии начинает терять детали и тащить дальше собственные прошлые ошибки.
Механизм от этого не страдает, а вот память — да. На DeepSeek такого нет.

## День 10 — три стратегии контекста

Задание дня 10 требует минимум трёх стратегий и переключателя между ними. Они
не исключают друг друга: включаются в любых сочетаниях, и интереснее всего именно
сочетания.

| Стратегия из задания | Где живёт | Чем управляется |
| --- | --- | --- |
| 1. Sliding Window | окно последних N сообщений, день 9 | `historyDepth` (сжатие безусловное) |
| 2. Sticky Facts | key-value память чата | `stickyFacts` |
| 3. Branching | ветки диалога | кнопка «чекпоинт» в шапке чата |

### Стратегия 2: sticky facts

Отдельный блок «ключ — значение», который уезжает в запрос третьим system-сообщением
после промпта чата и пересказа:

```
- имя: Влад
- проект: agent-sprout
- язык: Go
- дедлайн: пятница
```

Ключи свободные — модель придумывает их по ходу разговора; в промпте есть подсказка
про типовые категории из задания (цель, ограничения, предпочтения, решения,
договорённости). Потолок — 30 записей, иначе память однажды станет больше диалога,
который должна была заменить.

Чем отличается от пересказа:

| | Пересказ (день 9) | Факты (день 10) |
| --- | --- | --- |
| когда обновляется | на закрытии окна, раз в N сообщений | после каждой пары вопрос-ответ |
| что покрывает | только свёрнутую часть | весь чат с самого начала |
| закрытие окна | переписывается заново | переживает, копится дальше |
| как сбросить | очисткой истории | снять галочку или очистить историю |
| цена | вызов на N сообщений | **вызов на каждом ходе** |

Цена — главное, что надо понимать: факты удваивают число вызовов на ход. Поэтому
тумблер выключен по умолчанию.

**Отставание на один ход.** Память обновляется по паре «вопрос-ответ», а до вызова
ответа ещё нет. Значит в запрос хода N уезжает память, собранная по ходам до N-1
включительно: факт, названный только что, попадёт в контекст со следующего хода.

Сбой обновления памяти **не роняет ход**: ответ уже получен и оплачен, поэтому
ошибка уходит в предупреждение. Это осознанно отличается от сжатия, которое ход
отменяет, — сжатие происходит до вызова, и без него запрос не собрать.

### Стратегия 3: ветки диалога

Кнопка «чекпоинт» клонирует чат целиком: история, настройки и память переезжают
в новую ветку. У ветки свой тэг (задаётся при создании, уникальный) и время
отпочкования; больше ничем от обычного чата она не отличается.

Активным остаётся исходный чат — ветку создают, чтобы к ней вернуться, а не чтобы
немедленно в неё уйти. Два чекпоинта из одной точки дают две независимые ветки:
дальше диалоги расходятся, и их можно сравнивать. Ветку можно ответвить от ветки.

В списке слева это дерево:

```
чат 1
└ чат 1  [вариант-а]   14:02
└ чат 1  [вариант-б]   14:05
  └ чат 1  [б-уточнение]  14:09
```

### Зачем их сочетать

Окно режет диалог, пересказ сжимает то, что окно выбросило, факты переживают и то
и другое, а ветки дают одинаковую стартовую точку для сравнения. Показательный
прогон: включить факты и сжатие, довести чат до закрытия окна, сделать два чекпоинта
и в одной ветке выключить факты — дальше видно, что помнит агент с key-value памятью
и что остаётся без неё при одинаковом пересказе.

## День 11 — модель памяти и доменный помощник

С этого дня проект перестал быть чатом общего назначения: это помощник начинающего
строителя, и разговор в нём устроен как работа над **задачей** — одним видом работ
от постановки до плана. Без задачи слова «рабочая память» не к чему привязать,
а задание дня 11 требует развести память минимум на три слоя.

### Три слоя

| Слой | Что хранит | Где живёт | Когда очищается |
| --- | --- | --- | --- |
| **Краткосрочная** — диалог | окно последних сообщений, пересказ закрытого окна, итоги решённых задач чата | `Chat.Messages`, `Chat.Tasks[].Summary` | очисткой истории чата |
| **Рабочая** — задача | чеклист исходных данных активной задачи | `Chat.Tasks[активная].Requirements` | закрытием или прерыванием задачи |
| **Долговременная** — знания | заголовок и текст, независимо от чатов | общий справочник в хранилище | только руками пользователя |

Слои не пересекаются ни содержимым, ни временем жизни. В запрос каждый уезжает своим
system-сообщением со своей подписью — и модель понимает, что перед ней разные вещи,
и человек в снимке памяти видит, что откуда взялось.

### Жизненный цикл задачи

```
сообщение пользователя
      │  вне домена -> вежливый отказ, задача не заводится
      v
  инициализация: определён вид работ, составлен чеклист исходных данных (5-12 пунктов)
      │            если тема совпала с решённой задачей чата - ссылка на неё
      v
  сбор <-------+  уточняющие вопросы; второй вид работ -> отказ «сейчас делаем X»
      │        │
      v        │
  сверка ------+  собранное показывается списком, пользователь подтверждает или правит
      │
      v
  детальный пошаговый план -> задача закрыта, её итог уходит в память диалога
```

### Когда сбор заканчивается

Это главный вопрос машины, и **модели его не задают**: «достаточно ли данных» она
решит по-разному на одной и той же реплике. Критерий считает код:

1. при инициализации модель составляет чеклист под вид работ — от 5 до 12 пунктов;
2. дальше она только заполняет пункты и может добавить не больше двух новых за ход;
   удалять пункты нельзя, иначе чеклист сократится до нуля и сбор «закончится»;
3. когда все пункты заполнены, идёт **обязательный ход сверки**: агент показывает
   собранное и просит подтвердить. Шаг не формальный — диспетчер способен пометить
   пункт собранным, когда пользователь о нём и не заикался, и без сверки такая
   выдумка уехала бы прямо в план;
4. после подтверждения выдаётся план и задача закрывается;
5. **предохранитель**: если после восьми ходов опроса чеклист так и не полон, план
   выдаётся всё равно — с явным блоком «Допущения» по незаполненным пунктам.
   Бесконечный опрос это не дотошность, а зависание.

Пункт, который не подходит, закрывается значением «не применимо», а на который нет
ответа — «не знаю»: оба считаются заполненными, и второе честно попадёт в допущения.

### Страж переходов

Решение диспетчера — это текст от модели, то есть недетерминированная вещь. Поэтому
оно считается **заявкой**, а переход разрешает `task_guard.go` — чистая функция без
вызовов модели, целиком покрытая таблицей тестов.

| Состояние | Заявка | Что делает страж |
| --- | --- | --- |
| задачи нет | `collect` / `refuse_second` | в `start`, если назван вид работ, иначе в `ambiguous` |
| задачи нет | `start` без вида работ или без чеклиста | в `ambiguous` |
| задача идёт | `start` с другим видом работ | в `refuse_second`: молча начать вторую задачу нельзя |
| задачи нет | ответы вида «не знаю» на ходе инициализации | отбрасываются: человека ещё ни о чём не спрашивали |
| задача идёт | попытка убрать пункты чеклиста | пункты возвращаются на место |
| задача идёт | больше двух новых пунктов за ход | лишние отбрасываются |
| задача идёт | чеклист заполнен | в `confirm`, затем в `plan` — независимо от мнения модели |
| задача идёт | восемь ходов опроса позади | в `plan` с допущениями |

Строка про «не знаю» — из живого прогона: слабая модель на первом же ходе пометила
весь чеклист как «не знаю» и тем самым закрыла сбор, не задав ни одного вопроса.
На ходе опроса такое значение законно (вопрос задан, ответа нет — уйдёт в допущения),
а на инициализации взяться ему неоткуда.

Сверх переходов страж фиксирует заголовок задачи (модель любит переименовать
«штукатурные работы» в «оштукатуривание стен»), не даёт потерять собранное
и отбрасывает выдуманные ссылки на знания и на чужие задачи. Каждое понижение
пишется в трейс и в предупреждения: недетерминированность должна быть видна.

### Долговременная память

Справочник знаний общий для всех чатов: правило «железобетон делаем по СП 63»
не принадлежит ни одному разговору. Кнопка «знания» в шапке приложения, там же
**готовые заготовки** под частые виды работ — железобетон, кладка, штукатурка, полы,
кровля, фундаменты, охрана труда, расчёт материалов. Сами они не добавляются:
что лежит в долговременной памяти, пользователь решает явно.

Заготовки — отправная точка, а не истина: редакции сводов правил меняются, у объекта
бывает свой проект. Добавили — проверьте и поправьте под себя. Поэтому текст заготовки
читается **до** добавления — кнопка «посмотреть» разворачивает его прямо в списке;
решать, годится ли свод правил для этого объекта, по одному заголовку нельзя.
Сохранённое знание, наоборот, свёрнуто до четырёх строк с кнопкой «показать целиком»:
свод правил на полтора экрана иначе распирал панель так, что до соседних знаний
приходилось листать.

Под задачу знания отбирает модель по заголовкам, поэтому заголовок должен называть
тему, а не пересказывать текст.

### Что видно в интерфейсе

- **полоса состояния** над лентой — видна всегда: ожидание задачи, сбор с прогрессом
  чеклиста, сверка, план выдан, задача прервана. Разворачивается в рабочую память:
  чеклист с отметками, отобранные знания, решённые задачи диалога;
- **«память хода»** под каждым ответом — три подписанные секции с цветом слоя:
  какие знания подставились, что лежит в рабочей памяти, что дал диалог;
- кнопка **«прервать»** освобождает рабочую память, не трогая историю.

### Настройки: минимум

Редактор system prompt и пять пресетов из дня 3 убраны: доменная роль скрыта
и неизменяема, а поле, куда можно вписать «забудь про стройку», обесценило бы
и машину состояний, и слои памяти. Настройка `stickyFacts` тоже ушла — key-value
память никуда не делась, но теперь у неё есть хозяин, задача.

Остальное вычищено следом. Настройка имеет право на жизнь, только если ей
соответствует нынешняя логика приложения:

| Что убрано | Почему |
| --- | --- |
| формат ответа (`json_object`) | превратил бы детальный план работ в json |
| лимит слов | прямо противоречит «подробному пошаговому плану» |
| `top_p` | мы и так зануляли его при 1, а Liquid на него отвечает 400 |
| `frequency_penalty` / `presence_penalty` | на качество плана не влияют |
| сжатие истории | теперь безусловное, см. день 9 |
| судья | диагностика дня 10; к домену отношения не имеет |
| `max_tokens` | выводится из модели, см. ниже |

Осталось четыре: модель, `temperature`, окно истории, лимит длины запроса.

### Дефолты берутся из модели

Симптом был такой: чат с настройками по умолчанию работал, но стоило переключить
модель на flash — и ход падал с `context canceled` после 136 секунд
на шаге «машина состояний».

Причин оказалось три, и все три — про одни дефолты на все модели:

1. **`max_tokens` 4096 независимо от модели.** У рассуждающей модели в этот бюджет
   входит внутреннее рассуждение, и до видимого ответа дело просто не доходило.
2. **Служебные вызовы рассуждали там, где рассуждать не над чем** — у DeepSeek
   рассуждение включено по умолчанию, и сразу с максимальным усилием.
3. **Ход был привязан к `r.Context()`.** На 136-й секунде сдался не сервер (его
   таймаут был 3 минуты), а клиент — и вместе с ним погибла уже оплаченная работа.

Теперь у модели в каталоге есть собственные бюджеты:

| Модель | Контекст | Потолок вывода | Бюджет по умолчанию | Рассуждающая |
| --- | --- | --- | --- | --- |
| `liquid/lfm-2.5-2.6b:free` | 65 000 | 8 192 | 8 192 | нет |
| `deepseek-flash` | 1 000 000 | 384 000 | 16 000 | да |
| `deepseek-v4-pro` | 1 000 000 | 384 000 | 16 000 | да |

`max_tokens` — это потолок, а не счёт: за неизрасходованное не платят, а обрыв ответа
на середине стоит целого повторного вызова. Служебные вызовы берут бюджет оттуда же:
`Model.ServiceTokens(сколько нужно ответу)` добавляет запас на рассуждение, если модель
рассуждает, — страховка на случай, когда провайдер не принял выключатель рассуждения.
Пересчёт при смене модели живёт в `Chat.ApplyConfig` — там же, где проверка настроек,
чтобы правило нельзя было обойти мимо HTTP-слоя.

Результат на `deepseek-v4-pro`: ход занимает **11–20 секунд** против прежних
136 и более. На `deepseek-flash` то же самое проверить не удалось — в день правок
модель не отвечала вовсе: ни за две минуты, ни в потоковом режиме, ни с выключенным
рассуждением, тогда как `deepseek-v4-pro` на том же ключе и том же эндпоинте отвечал
за две секунды. Это сторона провайдера, а не приложения; приложение в этом случае
теперь честно говорит, что не дождалось, и не теряет ход.

### Чем ускорены служебные вызовы

Главное, что выяснилось про DeepSeek: **режим рассуждения включён по умолчанию,
и усилие в нём максимальное**. То есть за размышление мы платили всегда — в том числе
когда просили модель разложить одну реплику по полям json. Отсюда и 136 секунд
на диспетчере.

Переключатель у этого режима есть, он документирован
(https://api-docs.deepseek.com/guides/thinking_mode) и проверен запросом, а не взят
по памяти:

| Что отправили | Ответ | Токенов рассуждения |
| --- | --- | --- |
| как раньше (рассуждение по умолчанию) | 2 с | 40 из 43 |
| `{"thinking": {"type": "disabled"}}` | 2 с | 0 из 2 |

Поэтому диспетчер, сжатие и пересказ задачи уходят с выключенным рассуждением:
это извлечение и классификация, размышлять там не над чем. У ответа с планом
рассуждение остаётся полным — там оно по делу.

Оттуда же вторая находка: **в режиме рассуждения DeepSeek игнорирует `temperature`**
(и `presence_penalty` с `frequency_penalty` — ошибки не будет, эффекта тоже).
Ещё одна причина держать служебные вызовы вне этого режима: там `temperature = 0`
выставлена не для красоты.

Второй рычаг — **json-схема вместо свободного `json_object`** у диспетчера: со схемой
модель не может вернуть лишних полей, а `maxItems` не даёт слабой модели уйти
в бесконечный список и оборваться по бюджету на середине json.

### Откат, когда провайдер параметра не знает

Набор поддержанных параметров у провайдеров разный и меняется без предупреждения.
Поэтому `internal/llm/client.go` не гадает, а пробует:

> запрос уходит с ускоряющими параметрами; если провайдер ответил 400 и в теле
> упомянут параметр — повтор без него, с отметкой в трейсе. Какой именно параметр
> отвергли, запоминается для пары «провайдер + модель», чтобы следующий вызов
> не платил лишним кругом.

Откат **точечный**, и это не педантизм: DeepSeek json-схему не принимает
(«This response_format type is unavailable now»), а выключатель рассуждения принимает.
Скинуть их вместе значило бы вернуть себе то самое дорогое рассуждение, ради которого
всё и затевалось. Если из текста ошибки непонятно, что не понравилось, отбрасываются
оба — лучше потерять ускорение, чем зациклиться на отказах.

Контракт ответа при откате не теряется: вместо схемы уезжает обычный `json_object`,
то есть json остаётся, пропадает только гарантия формы.

### Ход больше не зависит от клиента

`Agent.Run` получает `context.WithoutCancel(r.Context())` со своим дедлайном.
Закрытая вкладка, потерянный wi-fi и нетерпеливый F5 больше не убивают оплаченный ход:
он дописывается до конца и сохраняется, а пользователь увидит его, когда вернётся.

Рядом ещё три мелочи из той же истории:

- **свой дедлайн на служебный вызов** (4 минуты) короче дедлайна хода (8 минут):
  зависший диспетчер не должен съесть весь бюджет и оставить ход без ответа;
- **честный текст по таймауту** — «ход не уложился в N секунд» вместо `context canceled`,
  который не говорит ни кто сдался, ни почему;
- **счётчик секунд** рядом с «агент работает»: на рассуждающей модели ход идёт десятками
  секунд, и неподвижная надпись неотличима от зависания.

### Оформление

Тема чёрно-жёлтая, как у строительной техники, но без игры в стройку: графит вместо
чёрного, приглушённый янтарь вместо кислотного жёлтого, плоские поверхности
и волосяные границы. Жёлтый здесь сигнал, а не фон.

Цвет заодно кодирует слой памяти: янтарь — рабочая, синька чертежа — долговременная,
бетон — краткосрочная. Шрифты — суперсемья IBM Plex в трёх начертаниях: Condensed
для подписей, Sans для текста планов, Mono для цифр и трейса. Вшиты в бандл через
`@fontsource`, без обращения к Google в рантайме.

## API

```
GET    /api/health
GET    /api/catalog                 модели, цены, бюджеты вывода, значения по умолчанию
GET    /api/chats                   список чатов со сводкой
POST   /api/chats                   создать
GET    /api/chats/{id}              чат с историей
PATCH  /api/chats/{id}              переименовать и/или изменить настройки
DELETE /api/chats/{id}              удалить
POST   /api/chats/{id}/checkpoint   клонировать чат в новую ветку с тэгом
POST   /api/chats/{id}/task/cancel  прервать активную задачу

GET    /api/knowledge               долговременная память и готовые заготовки
POST   /api/knowledge               {title, text}
PATCH  /api/knowledge/{id}
DELETE /api/knowledge/{id}
POST   /api/chats/{id}/messages     вопрос → ответ агента
DELETE /api/chats/{id}/messages     очистить историю, настройки сохранить
```

Ошибки приходят единым видом `{"error": {"code", "message"}}`. Коды: `input_policy`
и `output_policy` (422, штатная работа коробки), `bad_request` (400), `not_found` (404),
`tag_taken` (409, тэг ветки занят), `title_taken` (409, заголовок знания занят),
`no_active_task` (409), `provider` (502, авария снаружи). К ошибкам, которые уже изменили ленту, прикладывается
актуальный чат — вопрос и объяснение остаются в истории.

Маршрутизация — штатный `http.ServeMux` с паттернами Go 1.22+. Внешних зависимостей
у бэкенда нет ни одной.

## Хранилище

Чаты живут в памяти и после каждой мутации переписываются в JSON-файл (`DATA_FILE`)
через временный файл с переименованием — при падении посреди записи на диске останется
предыдущая целая версия. В compose файл лежит в volume, так что чаты и настройки
переживают пересборку контейнера.

```
DEFAULT_MODEL=deepseek-flash
```

Хватает одного ключа из двух: модели провайдера без ключа видны в списке, но помечены
как недоступные. `DEFAULT_MODEL` задаёт модель новых чатов — поставьте
`liquid/lfm-2.5-2.6b:free`, если хотите отлаживать бесплатно, не трогая код.

Остальные переменные: `PORT` (8080), `STATIC_DIR` (`/app/web`), `DATA_FILE`
(`/data/chats.json`), `LLM_TIMEOUT` (5 минут на один вызов модели, принимает
и `300`, и `5m`), `TURN_TIMEOUT` (8 минут на ход целиком: ход — это несколько
вызовов подряд), `APP_URL` — адрес приложения для атрибуции запросов в OpenRouter.

### Разработка без Docker

```bash
cd src/agent-sprout/backend && go run ./cmd/server     # :8080
cd src/agent-sprout/frontend && npm install && npm run dev   # :5174, прокси /api на :8080
```

Порт dev-сервера сдвинут на 5174 намеренно: 5173 занимает контейнер.
