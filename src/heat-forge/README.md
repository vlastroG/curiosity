# Heat Forge

Неделя 1, день 4 — влияние `temperature`.

Один и тот же запрос уходит тремя параллельными вызовами с разной температурой сэмплинга.
Всё остальное — модель, system prompt, `max_tokens` — одинаково для всех трёх; единственная
переменная эксперимента — `temperature`.

По заданию значения — 0, 0.7 и 1.2, но в интерфейсе это только дефолты: температура каждой
карточки редактируется прямо в её шапке (`<input type="number" step="0.1">`), можно поставить
любое число, включая одинаковые значения у нескольких карточек. Следующий прогон уйдёт
с новыми числами.

## Как это устроено

- `src/api.js` — `complete({ messages, system, temperature })`. В отличие от дня 3, где
  температура была зафиксирована константой модуля, здесь она обязательный параметр вызова:
  это единственное, что должно отличаться между тремя карточками.
- `src/temperatures.js` — `DEFAULT_TEMPERATURES = [0, 0.7, 1.2]` и `runAt(temperature, ...)`,
  один вызов без многошаговых цепочек. Общий `FORMAT_SYSTEM` (простой Markdown, без LaTeX,
  без таблиц) одинаков для всех трёх вызовов — без него модель на температуре 1.2 с той же
  вероятностью съезжает в LaTeX или широкую таблицу, которая не влезает в узкую колонку.
  В отличие от дня 3, здесь нет требования закончить ответ строкой "Ответ: ..." — сравнивается
  весь текст целиком, а не единственно верный итог.
- `src/App.jsx` — вопрос отправляется один раз и уходит в три параллельных вызова
  (`Promise.allSettled`). Поле ввода очищается сразу, поэтому сам вопрос показывается отдельной
  строкой над карточками и не пропадает, пока не будет отправлен следующий.
- `MAX_TOKENS = 100000` — модель рассуждающая (`deepseek-v4-flash`, как в дне 3), и `max_tokens`
  делится между внутренним рассуждением (`reasoning_content`) и видимым ответом. Если лимит
  исчерпан, приходит `finish_reason: "length"` и пустой `content` — вместо пустой карточки
  интерфейс показывает объяснение (`meta__warn` с текстом `finish: length`).

## Сравнение

Творческий вопрос показывает разницу нагляднее, чем арифметика — там температура почти
не видна, пока не начинают путаться в счёте. Задача:

> Придумай одно необычное название для кофейни в космическом стиле. Ответь одним названием
> без пояснений.

Два прогона одного и того же вопроса на дефолтных 0 / 0.7 / 1.2:

| temperature | Прогон 1 | Прогон 2 | Латентность | Токены |
| --- | --- | --- | --- | --- |
| 0 | «Кофейная туманность» | «Кофейная Туманность» | 18.2 с / 2.3 с | 2225 / 433 |
| 0.7 | «Орбита эспрессо» | «Космос в чашке» | 6.8 с / 1.6 с | 943 / 302 |
| 1.2 | «Кофейная сингулярность» | «Галактическая гуща» | 11.4 с / 2.4 с | 449 / 449 |

### Отличаются ли ответы

При `temperature = 0` два прогона дали практически один и тот же ответ — отличается только
регистр буквы. Это ожидаемо: нулевая температура убирает случайность сэмплинга, модель почти
всегда выбирает самый вероятный следующий токен, и на короткой генерации это даёт устойчивый
результат.

При `0.7` и `1.2` ответы разошлись оба раза — ни одно название не повторилось между прогонами.
На `1.2` формулировки заметно смелее и неожиданнее («сингулярность», «галактическая гуща»
вместо более предсказуемых «туманность»/«орбита»), хотя выборка из двух прогонов маловата,
чтобы утверждать это как строгую закономерность — для этого нужны десятки прогонов на каждую
температуру.

### Что ещё стоит иметь в виду

Первый прогон был явно медленнее и дороже второго (18.2 с и 2225 токенов против 2.3 с и 433
на той же температуре 0) — сказался холодный старт: это был первый запрос в сессии браузера.
Абсолютные цифры латентности и токенов в этой таблице поэтому меньше говорят о температуре
и больше — о состоянии сети/API в момент запроса; для честного сравнения стоимости лучше
смотреть на разницу между прогонами, а не на абсолютные значения одного прогона.

## Запуск

```bash
docker compose -f src/heat-forge/docker-compose.yml up --build
```

Затем http://localhost:5177

Без compose:

```bash
docker build -t heat-forge ./src/heat-forge
docker run -p 5177:80 -e DEEPSEEK_API_KEY=sk-your-key-here heat-forge
```

Ключ берётся из `.env` в корне репозитория (`DEEPSEEK_API_KEY=...`). При старте контейнера
`docker-entrypoint.sh` записывает его в `env-config.js`, откуда он попадает в `window._env_`.

## Ограничение по безопасности

Бэкенда нет: собранная статика отдаётся nginx, а запросы к DeepSeek уходят прямо из браузера.
Значит, ключ виден в исходниках страницы любому, кто её откроет. Для локального учебного
приложения это приемлемо, для публичного развёртывания — нет: там нужен серверный прокси,
который держит ключ у себя.
